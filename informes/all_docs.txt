[Heading 1] 1. Descripción general del problema
[] El proyecto RePoints busca automatizar la identificación de residuos de plástico y vidrio mediante una cámara USB conectada a una Raspberry Pi 5. Un modelo de inteligencia artificial procesa la imagen del residuo, predice su clase (plástico, vidrio o desconocido) y un módulo de sistema experto valida ese resultado aplicando reglas sobre el porcentaje de confianza antes de almacenarlo y mostrarlo en un dashboard web.
[] Para poder entrenar el clasificador de imágenes se requiere un dataset etiquetado de residuos de plástico y vidrio. Este informe documenta el origen, la calidad, la limpieza y la preparación del dataset elegido, siguiendo la rúbrica de análisis de dataset del proyecto integrador.
[] Un requisito particular del proyecto es que el modelo debe distinguir correctamente botellas de plástico transparente (PET) de botellas de vidrio, ya que ambos materiales pueden lucir visualmente similares (transparencia, brillo, forma cilíndrica) frente a una cámara. Por esto se buscó explícitamente un dataset que incluyera botellas plásticas transparentes junto a envases de vidrio.
[Heading 1] 2. Origen del dataset
[] Nombre: Drinking Waste Classification
[] Fuente: Kaggle (kaggle.com/datasets/arkadiyhacks/drinking-waste-classification)
[] Autor: Arkadiy Serezhkin
[] Licencia: CC0: Public Domain (uso libre, incluido uso académico/comercial)
[] Contexto de recolección: Proyecto de fin de carrera (Individual Project) en University College London (UCL). Las fotografías fueron tomadas manualmente con una cámara de teléfono de 12 MP como parte de un sistema de detección de residuos en tiempo real basado en YOLO.
[] Procedencia mixta: El propio autor indica que la clase PET incorpora parte del dataset TrashNet (Gary Thung y Mindy Yang, UCL/Stanford), lo cual explica los duplicados detectados en la sección 5.
[] El dataset original contiene 4 clases de residuos de bebidas: latas de aluminio (AluCan), botellas de vidrio (Glass), botellas PET de plástico transparente (PET) y botellas de leche HDPE (HDPEM), con un total de 14 500 archivos (1.63 GB), incluyendo además una copia anotada en formato YOLO no utilizada en este proyecto.
[] Pertinencia: para RePoints solo interesa distinguir plástico vs. vidrio, por lo que se seleccionaron únicamente las carpetas Glass y PET, descartando AluCan (metal) y HDPEM (plástico opaco, fuera del alcance). La clase PET es además la más relevante para el caso de botellas transparentes que el sistema experto debe resolver con las reglas de confianza.

[List Paragraph] Clase (plástico / vidrio) — variable objetivo, derivada del nombre de carpeta.

[Heading 1] 5. Limpieza y preprocesamiento
[Heading 2] 5.1 Eliminación de duplicados
[] Se calculó el hash MD5 exacto y el hash perceptual (pHash) de cada imagen. Se encontraron 70 grupos de duplicados exactos (140 archivos involucrados, 70 redundantes), y 71 grupos casi-idénticos por pHash. La totalidad de los duplicados se concentra dentro de la clase plástico (PET) — 0 casos cruzan clases — lo cual es consistente con que el autor combinó su propia captura con imágenes reutilizadas de TrashNet para esa clase. Se conservó 1 imagen por grupo y se eliminaron las 70 copias redundantes.
[Heading 2] 5.2 Eliminación de imágenes corruptas / formato no soportado
[] 8 imágenes de la clase vidrio estaban en formato HEIC (formato nativo de fotos de iPhone), no legible por el decodificador estándar (Pillow) usado en el pipeline de entrenamiento — se reportaron inicialmente como "corruptas" al fallar la verificación. En lugar de descartarlas, se instaló soporte HEIF (pillow-heif) y se convirtieron las 8 imágenes a JPG, conservando así el 100% de los datos disponibles. No se encontraron imágenes verdaderamente corruptas (0 bytes, cabecera dañada, etc.) en el subset.
[Heading 2] 5.3 Corrección de etiquetas erróneas
[] Al no existir duplicados que crucen entre clases (plastico vs. vidrio) y al provenir cada carpeta de una fuente etiquetada manualmente por el autor original, no se identificaron errores evidentes de etiquetado. Como control adicional, se revisaron visualmente las muestras representativas (figuras 2 y 3) y los casos de menor calidad (figura 5), sin encontrar imágenes mal clasificadas.
[Heading 2] 5.4 Redimensionamiento y normalización
[] Las imágenes originales tienen resoluciones heterogéneas (512×683, 512×384, 384×512 y un outlier de 4032×3024). Para el entrenamiento se aplicará, dentro del pipeline de carga de datos (tf.data / ImageDataGenerator), redimensionamiento a 224×224 px — tamaño estándar de entrada de MobileNetV2, la arquitectura prevista para ejecutar el modelo en la Raspberry Pi 5 vía TensorFlow Lite — y normalización de los valores de píxel al rango [0,1] (o al rango específico que exige el preprocesamiento de MobileNetV2). Se optó por aplicar este paso en tiempo de carga (on-the-fly) en vez de generar una copia redimensionada en disco, para no duplicar el almacenamiento y poder ajustar el tamaño de entrada si la arquitectura final cambia.
[Heading 1] 6. Balance del dataset
[] Antes de la limpieza: 1508 plástico vs. 1232 vidrio (razón 1.23:1). Después de eliminar los 70 duplicados de la clase plástico: 1438 plástico vs. 1232 vidrio (razón 1.17:1).
[] Figura 6. Distribución de clases del dataset limpio final (2670 imágenes).
[] Una razón de desbalance de 1.17:1 se considera leve (por debajo del umbral típico de preocupación de 1.5:1–2:1) y no exige técnicas agresivas de balanceo como SMOTE o undersampling severo. Aun así, para robustecer el entrenamiento se recomienda:
[List Paragraph] Usar class_weight balanceado en Keras/TensorFlow al compilar el modelo, para que los errores en la clase minoritaria (vidrio) pesen ligeramente más durante el entrenamiento.
[List Paragraph] Aplicar data augmentation (rotación, flip horizontal, variación de brillo) de forma algo más intensiva sobre la clase vidrio, para acercar el número efectivo de ejemplos vistos por época.
[Heading 1] 7. División para entrenamiento
[] La división se realizó de forma estratificada por clase (70/15/15), manteniendo en cada subconjunto la misma proporción plástico:vidrio que el dataset completo, y usando una semilla fija (random_state=42) para que el split sea reproducible.
[] Justificación: 70% para entrenamiento es suficiente dado el tamaño del dataset (1868 imágenes) para hacer transfer learning sobre una red preentrenada (MobileNetV2) sin sobreajustar de inmediato; 15% de validación permite monitorear el sobreajuste y ajustar hiperparámetros durante el entrenamiento; el 15% de prueba queda completamente aislado hasta la evaluación final, para obtener una medida honesta del desempeño antes de desplegar el modelo en la Raspberry Pi.
[Heading 1] 8. Riesgos y limitaciones del dataset
[List Paragraph] Cero imágenes tomadas en el contexto real del proyecto (universidad, cámara USB frontal sobre la Raspberry Pi 5): todas las fotos provienen de un entorno doméstico ajeno al de despliegue final.
[List Paragraph] Variabilidad de fondo muy limitada: el vidrio se fotografió siempre sobre el mismo piso de madera y el plástico siempre sobre el mismo mantel a cuadros — alto riesgo de que el modelo memorice el fondo en lugar del objeto (shortcut learning).
[List Paragraph] Ángulo de captura uniforme: casi todas las fotos son tomas cenitales (de arriba hacia abajo); la cámara USB del proyecto probablemente capturará el objeto de frente o en ángulo, lo que representa un cambio de dominio (domain shift).
[List Paragraph] Iluminación homogénea de interior: no hay variabilidad de luz natural/exterior ni de sombras duras, que sí podrían aparecer en el punto de uso real.
[List Paragraph] Objetos parcialmente ocultos o encuadres muy cerrados en un subconjunto de imágenes (ver figura 5), lo que reduce la información visual disponible en esos casos.
[List Paragraph] Redundancia original en la clase PET por mezcla con TrashNet (ya mitigada con la eliminación de 70 duplicados, pero reduce la diversidad real neta de esa clase).
[List Paragraph] Formato HEIC no estándar en 8 imágenes (ya solucionado, pero indica que el pipeline de producción deberá aceptar o normalizar múltiples formatos de imagen).
[List Paragraph] Riesgo de sobreajuste (overfitting): dado el fondo y ángulo repetitivos, el modelo puede lograr alta precisión en el conjunto de prueba (que comparte el mismo sesgo) pero comportarse mal frente a las fotos reales de la Raspberry Pi.
[List Paragraph] Ambigüedad plástico transparente vs. vidrio transparente: aunque se priorizó un dataset con botellas PET transparentes, no hay garantía de que cubra todos los casos límite (p. ej. vidrio muy claro/transparente vs. plástico transparente bajo la misma iluminación) que el sistema experto deberá resolver con el umbral de confianza.
[Heading 1] 9. Estrategia para mejorar el dataset
[List Paragraph] Captura propia en la universidad: tomar fotografías reales con la misma Raspberry Pi 5 y cámara USB que se usará en producción, variando fondo (piso, mesa, césped/cancha), ángulo y hora del día, e incorporarlas como conjunto de fine-tuning o como parte del conjunto de prueba "del mundo real".
[List Paragraph] Data augmentation en el pipeline de entrenamiter: rotación aleatoria (±20°), flip horizontal, cambios de brillo/contraste (±20%), zoom aleatorio y ligero recorte, para simular la variabilidad de fondo/iluminación que el dataset original no cubre.
[List Paragraph] Diversificar fondos deliberadamente en la captura propia (evitar repetir el mismo mantel/piso en todas las fotos), para romper la asociación fondo-clase que existe en el dataset base.
[List Paragraph] Incluir explícitamente más ejemplos de botellas de plástico transparente vacías y de vidrio transparente/claro fotografiadas bajo condiciones similares, para reducir el riesgo de confusión que debe resolver el sistema experto.
[List Paragraph] Complementar con un segundo dataset público (por ejemplo TrashNet o Garbage Classification, filtrando solo las clases glass/plastic) únicamente como fuente adicional de variabilidad visual, no como reemplazo del dataset principal.
[List Paragraph] Mantener el umbral de confianza del sistema experto (≥85% aceptar, 60–84% solicitar recaptura, <60% desconocido) como mecanismo de seguridad mientras el dataset y el modelo maduran con datos reales.
[Heading 1] 10. Conclusiones
[] ¿El dataset es suficiente para entrenar el modelo? Sí, en cantidad: 2670 imágenes limpias (1868 de entrenamiento) son un punto de partida razonable para un MVP basado en transfer learning con MobileNetV2, especialmente combinado con data augmentation. No es suficiente, en cambio, en variabilidad de contexto: fondo, ángulo e iluminación están muy poco representados en comparación con el entorno real de despliegue.
[] ¿Qué problemas presenta? Un desbalance leve (1.17:1, manejable), 70 duplicados dentro de la clase plástico (ya eliminados), 8 imágenes en formato HEIC no estándar (ya convertidas), y sobre todo un fondo y ángulo de captura extremadamente repetitivos que no reflejan el punto de uso final del sistema (Raspberry Pi + cámara USB en la universidad).
[] ¿Qué acciones se realizarán para mitigarlos? Se aplicó ya la limpieza (deduplicación y conversión de formato) y la división estratificada 70/15/15 documentadas en este informe. Antes de considerar el modelo listo para producción, se planea complementar el dataset con capturas propias en el entorno real del proyecto y aplicar data augmentation agresiva orientada a variar fondo, ángulo e iluminación, validando el desempeño final sobre ese conjunto de prueba "del mundo real" y no únicamente sobre el test set derivado del dataset de Kaggle.

[Heading 1] 1. Definición del problema y objetivos
[Heading 2] 1.1 Problema
[] Actualmente la separación de residuos de plástico y vidrio dentro del campus universitario se realiza de forma manual, dependiendo del criterio de cada persona. Esto provoca contaminación cruzada entre materiales reciclables y reduce la eficiencia de los procesos de reciclaje posteriores. RePoints propone automatizar esta clasificación mediante visión por computador embebida en una Raspberry Pi 5, apoyada por un módulo de sistema experto que valida la predicción del modelo antes de aceptarla como definitiva.
[Heading 2] 1.2 Objetivo general
[] Diseñar una solución de inteligencia artificial capaz de clasificar en tiempo real residuos de plástico y vidrio a partir de una imagen capturada por cámara, integrando un modelo de visión por computador con un módulo de reglas (sistema experto) que valide la confianza de cada predicción antes de tomar una decisión final.
[Heading 2] 1.3 Objetivos específicos
[List Paragraph] Seleccionar y justificar una arquitectura de red neuronal adecuada para clasificación binaria de imágenes bajo restricciones de hardware embebido (Raspberry Pi 5, sin GPU dedicada).
[List Paragraph] Definir un flujo de entrenamiento reproducible (partición de datos, hiperparámetros, función de pérdida y optimizador) a partir del dataset limpio y dividido documentado en el informe de análisis del dataset.
[List Paragraph] Establecer una estrategia de validación basada en métricas estándar de clasificación que permita detectar sobreajuste y sesgo entre clases.
[List Paragraph] Identificar los riesgos técnicos propios del entorno real de despliegue (iluminación variable, fondos no controlados, materiales transparentes) y definir estrategias de mitigación.
[Heading 2] 1.4 Alcance
[] Tipo de clasificación: Binaria (plástico vs. vidrio), con manejo adicional de una categoría operativa "desconocido" cuando la confianza del modelo es insuficiente.
[] Entradas: Imagen RGB de un residuo, capturada por una cámara USB conectada a la Raspberry Pi 5, en el momento en que el objeto se coloca frente al sensor.
[] Salidas: Etiqueta de clase (plástico / vidrio / desconocido), probabilidad de confianza asociada, y registro del resultado en un dashboard web para su trazabilidad.
[] Fuera de alcance: Clasificación de otros materiales (metal, papel, orgánico) y control físico de actuadores de separación, que corresponden a otras materias del proyecto integrado y no a este diseño.
[Heading 1] 2. Arquitectura del sistema
[] La figura 1 presenta el flujo completo de la solución, desde la captura física de la imagen hasta la decisión final validada y su registro.
[] Figura 1. Arquitectura de la solución RePoints: pipeline de captura, preprocesamiento, inferencia, validación por sistema experto y salida.
[Heading 2] 2.1 Descripción de componentes
[List Paragraph] Cámara USB (hardware): sensor de captura conectado físicamente a la Raspberry Pi 5; adquiere la imagen del residuo cuando se activa la rutina de captura.
[List Paragraph] Captura de imagen (Raspberry Pi 5): proceso en la propia placa que lee el frame de la cámara y lo entrega al pipeline de software para su procesamiento.
[List Paragraph] Preprocesamiento: redimensiona la imagen a 224×224 px (entrada esperada por MobileNetV2) y normaliza los valores de píxel al rango que exige el preprocesamiento de la red preentrenada.
[List Paragraph] Modelo de IA (MobileNetV2, exportado a TensorFlow Lite): recibe el tensor preprocesado y produce una probabilidad por clase (plástico / vidrio).
[List Paragraph] Clasificación: combina la clase de mayor probabilidad con su nivel de confianza asociado, insumo directo para el sistema experto.
[List Paragraph] Sistema experto (reglas de confianza): valida la predicción aplicando umbrales — confianza ≥85% acepta la clase directamente; 60-84% solicita una recaptura de la imagen; <60% marca el resultado como "desconocido" en vez de forzar una clasificación poco confiable.
[List Paragraph] Decisión final e integración con hardware/dashboard: una vez validada, la clase se registra y visualiza en un dashboard web, quedando disponible como evidencia para las materias de Tecnologías de Plataforma y Manejo y Desarrollo de Proyectos del mismo proyecto integrador.
[] Esta separación entre "modelo que predice" y "sistema experto que decide" es intencional: permite ajustar el umbral de aceptación sin reentrenar el modelo, y da trazabilidad explícita a los casos límite (confianza media/baja) en vez de forzar siempre una respuesta binaria.
[Heading 1] 3. Modelo seleccionado y justificación
[Heading 2] 3.1 Alternativas consideradas
[Heading 2] 3.2 Justificación de MobileNetV2
[List Paragraph] Recursos computacionales: la Raspberry Pi 5 no cuenta con GPU dedicada; MobileNetV2 usa convoluciones separables en profundidad (depthwise separable convolutions), lo que reduce drásticamente el número de parámetros (~3.4M) y operaciones frente a redes clásicas (VGG, ResNet), permitiendo inferencia en CPU en tiempos de cientos de milisegundos.
[List Paragraph] Precisión esperada: para un problema binario con clases visualmente distinguibles (forma, color, transparencia), el transfer learning desde ImageNet ya provee filtros de bajo/medio nivel (bordes, texturas, transparencias) reutilizables, por lo que se espera una precisión de validación alta (>90%) incluso con un dataset de tamaño moderado.
[List Paragraph] Tiempo de inferencia: al exportar el modelo entrenado a TensorFlow Lite (formato .tflite) se habilita cuantización (float16 / int8), reduciendo aún más el tamaño del modelo y el tiempo de inferencia en la Raspberry Pi, un requisito crítico para una clasificación en tiempo real.
[List Paragraph] Factibilidad de implementación: MobileNetV2 tiene soporte de primera clase en TensorFlow/Keras y en TensorFlow Lite, con abundante documentación y ejemplos de despliegue en Raspberry Pi, lo que reduce el riesgo técnico de esta fase del proyecto.

[Heading 1] 5. Estrategia de validación del modelo
[] Dado que el dataset presenta un desbalance leve entre clases (1438 vs. 1232), la exactitud (accuracy) por sí sola puede ocultar un desempeño pobre en la clase minoritaria. [Heading 1] 6. Riesgos técnicos
[Heading 1] 7. Estrategias de mejora
[List Paragraph] Data augmentation: rotación, flip horizontal, variación de brillo/contraste y zoom aleatorio aplicados en tiempo de carga, para compensar la baja variabilidad de fondo/iluminación del dataset original.
[List Paragraph] Transfer learning en dos fases: entrenamiento inicial con la base MobileNetV2 congelada seguido de fine-tuning de las últimas capas, para adaptar los filtros preentrenados al dominio específico de residuos de plástico y vidrio sin perder el conocimiento general de ImageNet.
[List Paragraph] Ajuste de hiperparámetros: búsqueda acotada sobre learning rate, número de capas descongeladas y peso de clases, comparando resultados mediante F1-score en el conjunto de validación antes de fijar la configuración final.
[List Paragraph] Captura de imágenes reales dentro de la universidad: complementar el dataset de Kaggle con fotografías tomadas con la misma cámara USB y Raspberry Pi 5 del proyecto, en el entorno real de despliegue, usadas como conjunto adicional de validación "del mundo real" antes de aceptar el modelo como definitivo.

[Normal] REPOINTS
[Heading 1] PARTE 1: -INTEGRANTE 1 INTRODUCCIÓN, PROBLEMA Y ARQUITECTURA DE HARDWARE
[Normal] "Para resolver esto, hemos desarrollado RePoints, que está diseñado bajo el concepto de una máquina expendedora inversa, o Reverse Vending Machine.
[Normal] A nivel de arquitectura de hardware, el núcleo de procesamiento es una Raspberry Pi 5. El flujo físico y de información es el siguiente:
[Normal] Primero, el usuario interactúa con el sistema donde una cámara se encarga de leer su código QR de identidad. Luego, una segunda cámara captura el objeto ingresado. Esta imagen se redimensiona a 224x224 píxeles y pasa a nuestro Modelo de Inteligencia Artificial, el cual predice una probabilidad de clasificación."
[Normal] "Aquí es donde entra la innovación de nuestro diseño: la IA no toma la decisión final por sí sola. La probabilidad pasa a un Sistema Experto basado en reglas lógicas.
[Normal] Si la confianza es mayor o igual al 85%, el material, ya sea plástico o vidrio, es aceptado y clasificado mecánicamente. Si está entre 60% y 84%, el sistema pide que se vuelva a acomodar el residuo para una recaptura... y si es menor a 60%, lo marca directamente como 'desconocido'.
[Normal] Esto evita errores forzados en la clasificación física."
[Heading 1] PARTE 2: -INTEGRANTE 2 ANÁLISIS, LIMPIEZA Y PREPARACIÓN DEL DATASET
[Normal] Origen de los Datos: "Continuando con el flujo, un modelo robusto requiere datos de calidad. Utilizamos como base el dataset público 'Drinking Waste Classification' de Kaggle, que incluía aportes del reconocido dataset TrashNet. De las 14,500 imágenes originales y 4 clases disponibles, filtramos estrictamente las carpetas de vidrio (Glass) y botellas de plástico transparente (PET), ya que la distinción entre estos dos materiales transparentes es nuestro objetivo principal."
[Normal] Limpieza y Preprocesamiento: "Durante el Análisis Exploratorio de Datos (EDA), detectamos problemas que debían corregirse antes del entrenamiento. Identificamos y eliminamos 70 imágenes duplicadas en la clase de plástico mediante el cálculo de hashes MD5 y hashes perceptuales (pHash). Además, convertimos 8 imágenes que venían en formato HEIC a JPG instalando soporte específico (pillowheif) para no perder datos."
[Normal] Partición y Balance: "Nuestro dataset final quedó conformado por 2670 imágenes: 1438 de plástico y 1232 de vidrio. Al ser un desbalance leve (1.17:1), aplicamos 'class_weight' en el entrenamiento. Finalmente, dividimos el dataset de manera estratificada con una semilla fija (random_state 42) en 70% para entrenamiento (1868 fotos), 15% para validación (399 fotos) y 15% para pruebas aisladas (403 fotos)."
[Heading 1] PARTE 3: INTEGRANTE 3 - DISEÑO DEL MODELO DE INTELIGENCIA ARTIFICIAL
[Normal] Justificación de la Arquitectura: "Para el motor de clasificación visual, evaluamos varias opciones, incluyendo entrenar una CNN desde cero, YOLO o EfficientNet. Nos decantamos por MobileNetV2 por una razón fundamental: las restricciones de nuestro hardware. La Raspberry Pi 5 no cuenta con una GPU dedicada, y MobileNetV2 utiliza convoluciones separables en profundidad (depthwise separable convolutions), lo que reduce sus parámetros a solo 3.4 millones. Esto nos da un equilibrio perfecto entre bajo costo computacional y alta precisión."
[Normal] Estrategia de Transfer Learning: "Dado que 2670 imágenes es un volumen pequeño para entrenar desde cero, aplicamos Transfer Learning. Importamos los pesos preentrenados del inmenso dataset ImageNet. Esta base ya sabe detectar bordes, texturas y brillos, características vitales para distinguir las propiedades ópticas del vidrio frente al plástico PET."
[Normal] Riesgos Detectados: "En la fase de diseño prevemos dos grandes retos técnicos: el primero, la similitud visual entre plástico y vidrio transparente. El segundo, detectamos que el dataset tenía fotos tomadas siempre desde un ángulo cenital y con fondos muy repetitivos (un mantel a cuadros para el plástico y un piso de madera para el vidrio), lo que genera un riesgo de 'shortcut learning' o memorización del fondo. Por ello, planificamos estrategias estrictas de validación."
[Heading 1] PARTE 4: INTEGRANTE 4 - FLUJO DE ENTRENAMIENTO Y EXPORTACIÓN
[Normal] Configuración del Entrenamiento: "El entrenamiento lo ejecutamos en CPU durante 854 segundos, utilizando el optimizador Adam y Binary Crossentropy como función de pérdida, dado que es una clasificación binaria con activación Sigmoide. Aplicamos Data Augmentation en tiempo de carga (rotaciones de ±20°, zoom, flips horizontales y alteraciones de contraste) para mitigar el riesgo de memorización de fondos que mencionó mi compañero."
[Normal] Las Dos Fases de Aprendizaje: "Implementamos el entrenamiento en dos fases muy controladas. En la Fase 1 (12 épocas con learning rate de 1e-4), congelamos toda la base de MobileNetV2 y entrenamos únicamente nuestra nueva capa clasificadora superior. En la Fase 2 (10 épocas con learning rate más bajo de 1e-5), descongelamos las últimas 30 capas de la red para hacer un 'fine-tuning' y especializar los filtros directamente en nuestros residuos, utilizando Early Stopping para evitar el sobreajuste."
[Normal] Despliegue y Optimización: "El modelo resultante (.keras de ~20MB) era muy pesado. Para llevarlo a la Raspberry Pi, lo convertimos y cuantizamos al formato TensorFlow Lite (.tflite), reduciendo su tamaño a solo 2.41 MB, optimizando su consumo de memoria RAM sin sacrificar precisión."
[Heading 1] PARTE 5: INTEGRANTE 5 - RESULTADOS, INTEGRACIÓN WEB Y CONCLUSIONES
[Normal] Evaluación de Métricas: "Los resultados sobre nuestro conjunto de pruebas, el cual estuvo completamente aislado, fueron excelentes. Logramos un Accuracy (precisión global) del 97.02%, con un F1-Score ponderado de 0.9701. Al observar la matriz de confusión, el modelo acertó en las 217 imágenes de plástico y en 174 de vidrio; tuvimos solo 12 falsos positivos donde el vidrio fue clasificado como plástico, validando nuestra hipótesis de que la ambigüedad de los materiales transparentes es el mayor desafío límite."

[Heading 1] 0. Resumen ejecutivo (lo primero que debe salir de memoria)
[Heading 1] 1. Bloque: Arquitectura y hardware
[] P: ¿Por qué se llama 'máquina expendedora inversa' (Reverse Vending Machine)?
[] R: Porque en vez de entregar un producto a cambio de dinero, el usuario introduce un residuo (plástico o vidrio) y el sistema le entrega puntos de reciclaje a cambio, tras validar el material.
[] P: Describan el flujo completo de principio a fin.
[] R: 1) Una cámara lee el código QR del usuario para identificarlo. 2) Una segunda cámara captura la imagen del residuo. 3) La imagen se redimensiona a 224×224 px y se normaliza. 4) El modelo MobileNetV2 (TFLite) produce una probabilidad de clase (plástico/vidrio). 5) Esa probabilidad pasa al Sistema Experto, que aplica las reglas de confianza y emite la decisión final. 6) Si se acepta, la transacción se registra en el dashboard web (RePoints) y se asignan puntos al usuario.
[] P: ¿Por qué la Raspberry Pi 5 y no otro hardware con GPU?
[] R: Es una restricción de diseño del proyecto integrador (bajo costo, portabilidad, integración física en un prototipo de campus). Al no tener GPU dedicada, el modelo de IA tuvo que elegirse específicamente para ser eficiente en CPU: por eso MobileNetV2 y no una CNN pesada tipo VGG/ResNet.
[] P: ¿Por qué la IA no decide sola?
[] R: Porque ningún modelo es 100% confiable, y un error de clasificación físico (mandar vidrio a la tolva de plástico) es costoso de revertir. El Sistema Experto añade una capa de reglas explicables y ajustables sin reentrenar el modelo: solo se acepta la predicción si la confianza es alta; si es media se pide recaptura; si es baja se marca 'desconocido' en vez de forzar una clase.
[Heading 1] 2. Bloque: Dataset — origen, limpieza y balance
[] P: ¿De dónde salieron las imágenes?
[] R: Del dataset público de Kaggle 'Drinking Waste Classification' (autor Arkadiy Serezhkin, licencia CC0), originado en un proyecto de fin de carrera en UCL. Tiene 4 clases (latas, vidrio, PET, HDPE) y 14,500 imágenes en total; nosotros solo usamos las carpetas Glass y PET porque el proyecto es binario (plástico vs. vidrio).
[] P: ¿Por qué hay duplicados y de dónde vienen?
[] R: El propio autor del dataset combinó su captura propia con imágenes reutilizadas de TrashNet (Thung & Yang, UCL/Stanford) específicamente en la clase PET, lo que generó 70 duplicados exactos dentro de esa clase. No hay duplicados que crucen entre clases.
[] P: ¿Cómo detectaron y eliminaron los duplicados?
[] R: Calculando hash MD5 exacto (para duplicados idénticos byte a byte) y hash perceptual pHash (para casi-idénticos) de cada imagen. Se encontraron 70 grupos de duplicados exactos (140 archivos, 70 redundantes) y se conservó 1 imagen por grupo, eliminando las 70 copias.
[] P: ¿Qué pasó con las imágenes HEIC?
[] R: 8 imágenes de la clase vidrio venían en formato HEIC (nativo de iPhone), no legible por Pillow estándar. En vez de descartarlas, se instaló soporte HEIF (pillow-heif) y se convirtieron a JPG, conservando el 100% de los datos.
[] P: ¿Cuántas imágenes quedaron al final y cómo se dividieron?
[] R: 2670 imágenes limpias: 1438 plástico y 1232 vidrio (antes de limpiar eran 1508 y 1232, razón 1.23:1; después de quitar los 70 duplicados de plástico, razón 1.17:1).
[] R: División estratificada 70/15/15 con semilla fija random_state=42: Entrenamiento 1868 (1006 plástico / 862 vidrio), Validación 399 (215 / 184), Prueba 403 (217 / 186).
[] P: ¿Por qué no balancearon las clases con SMOTE o undersampling?
[] R: Porque la razón de desbalance final (1.17:1) está muy por debajo del umbral típico de preocupación (1.5:1–2:1), así que se consideró leve. En su lugar se usó 'class_weight' balanceado en el entrenamiento, una técnica más suave que no descarta ni genera datos sintéticos.
[] P: ¿Qué limitaciones tiene el dataset y cómo las manejaron?
[] R: El riesgo principal es 'shortcut learning': el plástico siempre se fotografió sobre el mismo mantel a cuadros y el vidrio siempre sobre el mismo piso de madera, casi todas las fotos son cenitales, y la iluminación es homogénea de interior. El modelo podría aprender el fondo en vez del objeto.
[] R: Se mitigó con data augmentation agresivo (rotación ±20°, flip horizontal, zoom, variación de contraste/brillo) y quedó documentado como trabajo futuro capturar fotos reales en el campus con la misma cámara/Raspberry Pi para reentrenar y cerrar la brecha de dominio (domain shift).
[Heading 1] 3. Bloque: Diseño del modelo
[] P: ¿Por qué MobileNetV2 y no una CNN propia, YOLO o EfficientNet?
[] R: CNN propia: requeriría muchos más datos y tiempo para igualar a un modelo preentrenado; 2670 imágenes es poco para entrenar desde cero.
[] R: YOLO: está pensado para detección con múltiples objetos y bounding boxes; nuestro caso es clasificación de un solo objeto centrado, así que sería complejidad innecesaria.
[] R: EfficientNet-B0: mejor precisión relativa en benchmarks generales, pero mayor costo computacional/memoria que MobileNetV2 para una ganancia marginal en un problema binario relativamente simple.
[] R: MobileNetV2: usa convoluciones separables en profundidad (depthwise separable convolutions), reduce los parámetros a ~3.4 millones, corre bien en CPU sin GPU, y tiene soporte de primera clase en TensorFlow Lite para desplegar en la Raspberry Pi.
[] P: ¿Qué es transfer learning y por qué lo usaron?
[] R: Es reutilizar los pesos de una red ya entrenada en un dataset masivo (ImageNet, millones de imágenes) en vez de entrenar desde cero. Esa base ya sabe detectar bordes, texturas y brillos, características clave para distinguir las propiedades ópticas del vidrio frente al plástico PET. Con solo 2670 imágenes propias, entrenar desde cero no habría sido viable.
[] P: ¿Cómo está compuesta exactamente la arquitectura final?
[] R: Base MobileNetV2 preentrenada en ImageNet (~154 capas) + capas propias: GlobalAveragePooling2D + Dropout(0.2) + Dense(1, activación sigmoide). Es clasificación binaria (plástico=0 / vidrio=1), por eso una sola neurona de salida con sigmoide en vez de softmax con dos neuronas.
[] P: ¿Qué riesgos identificaron antes de entrenar?
[] R: 1) Similitud visual entre plástico y vidrio transparente (el reto central del proyecto). 2) El dataset tenía fondos y ángulos muy repetitivos (mantel a cuadros / piso de madera, toma cenital), lo que genera riesgo de que el modelo memorice el fondo en vez del material.
[Heading 1] 4. Bloque: Entrenamiento — 'cuántas veces entrenó el modelo'
[] P: ¿Cuántas veces se entrenó el modelo / cuántas épocas tuvo?
[] R: El entrenamiento se hizo en 2 fases. Se planificaron hasta 30 épocas con early stopping (paciencia=5 sobre val_loss), pero en la práctica el modelo convergió y se detuvo en 22 épocas efectivas: 12 en la Fase 1 y 10 en la Fase 2.
[] P: ¿Qué diferencia hay entre la Fase 1 y la Fase 2?
[] R: Fase 1 (12 épocas, learning rate 1e-4): toda la base de MobileNetV2 queda congelada (no se actualizan sus pesos); solo se entrena el clasificador nuevo que se añadió encima (GlobalAveragePooling + Dropout + Dense).
[] R: Fase 2 (10 épocas, learning rate más bajo 1e-5): se descongelan las últimas 30 capas de la base para hacer 'fine-tuning', es decir, especializar esos filtros al dominio específico de plástico/vidrio, con una tasa de aprendizaje baja para no destruir lo aprendido en ImageNet.
[] P: ¿Por qué bajar el learning rate en la Fase 2?
[] R: Porque al descongelar capas preentrenadas, un learning rate alto podría destruir de golpe los pesos ya aprendidos en ImageNet ('catastrophic forgetting'). Un LR bajo (1e-5) permite un ajuste fino y gradual. Además se usó ReduceLROnPlateau (factor 0.5, paciencia=3) para bajarlo automáticamente si la validación se estancaba.
[] P: ¿Cuánto tardó en entrenar y en qué hardware?
[] R: 854 segundos en total (~14.2 minutos), corriendo en CPU (sin GPU dedicada): 455.9 s la Fase 1 y 398.1 s la Fase 2.
[] P: ¿Qué función de pérdida y optimizador usaron, y por qué?
[] R: Binary Crossentropy, apropiada porque es clasificación binaria con salida sigmoide. Optimizador Adam, por su convergencia rápida y estable sin necesitar ajuste manual extenso de la tasa de aprendizaje. Batch size de 32, un balance estándar entre estabilidad del gradiente y uso de memoria.
[] P: ¿Qué es el 'class_weight' y para qué se usó aquí?
[] R: Es un peso que se le da a cada clase durante el entrenamiento para que los errores en la clase minoritaria (vidrio, 1232 imágenes frente a 1438 de plástico) penalicen más la función de pérdida, compensando el desbalance leve sin necesidad de eliminar o duplicar imágenes.
[] P: ¿Qué transformaciones de data augmentation aplicaron y por qué?
[] R: Rotación aleatoria (±20°), flip horizontal, zoom aleatorio (±15%) y variación de contraste/brillo (±20%), aplicadas solo al conjunto de entrenamiento y en tiempo de carga (no se guardan copias en disco). El objetivo es simular la variabilidad de fondo, ángulo e iluminación que el dataset original no tiene, para reducir el riesgo de 'shortcut learning'.
[] P: ¿Qué normalización se aplicó a las imágenes?
[] R: Redimensionamiento a 224×224 px (tamaño de entrada esperado por MobileNetV2) y la función preprocess_input propia de MobileNetV2, que reescala los valores de píxel al rango [-1, 1].
[Heading 1] 5. Bloque: Resultados y evaluación — 'qué votó el modelo'
[] P: ¿Qué accuracy y F1 obtuvieron y sobre qué conjunto?
[] R: Sobre el conjunto de prueba (403 imágenes, completamente aislado durante todo el entrenamiento): Accuracy global 97.02%, F1-score ponderado 0.9701 (F1 plástico 0.9731, F1 vidrio 0.9667).
[] R: Precision ponderada 0.9718 (plástico 0.9476, vidrio 1.0) y Recall ponderado 0.9702 (plástico 1.0, vidrio 0.9355).
[] P: Expliquen la matriz de confusión: ¿qué votó el modelo en cada caso?
[] R: De 217 imágenes reales de plástico, el modelo votó 'plástico' en las 217 (100% de acierto, 0 errores). De 186 imágenes reales de vidrio, el modelo votó 'vidrio' en 174 y 'plástico' en 12 (todos los errores del sistema están en esta dirección: vidrio confundido con plástico, nunca al revés).
[] P: ¿Por qué el modelo nunca confunde plástico con vidrio, pero sí vidrio con plástico?
[] R: Es una asimetría esperada dado el reto identificado desde el diseño: la ambigüedad óptica es mayor en un sentido porque el vidrio transparente/claro puede lucir muy similar al PET transparente bajo ciertas condiciones de brillo y encuadre, mientras que las botellas de plástico del dataset tienen rasgos más distintivos (tapa, forma, reflejos) que el modelo aprendió con más seguridad.
[] P: ¿Qué imágenes generan más confusión y por qué?
[] R: Principalmente imágenes con transparencia ambigua (PET transparente vs. vidrio claro) y encuadres o fondos que se apartan del patrón dominante del dataset (mantel a cuadros para plástico, piso de madera para vidrio). Es consistente con los dos riesgos anticipados desde la fase de diseño: la ambigüedad óptica es un límite físico del problema, y el fondo repetitivo puede haber generado asociaciones parciales entre fondo y clase.
[] P: ¿Hicieron alguna prueba adicional aparte de la matriz de confusión?
[] R: Sí, se evaluaron 24 imágenes nuevas del conjunto de prueba con 24 aciertos de 24 (100%), documentadas con su nivel de confianza individual en el archivo pruebas_modelo.csv (confianzas entre ~91% y 100%).
[] P: ¿Cuánto tarda el modelo en clasificar una imagen?
[] R: 139.7 milisegundos en promedio por imagen, medido en CPU, lo que es compatible con una clasificación en tiempo real dentro del flujo de la máquina expendedora inversa.
[] P: ¿Cómo se exportó el modelo final para la Raspberry Pi?
[] R: Primero se guardó en formato .keras (~20.88 MB) para seguir depurando en PC. Luego se convirtió y cuantizó a TensorFlow Lite (.tflite), reduciendo el tamaño a 2.41 MB, optimizando memoria RAM y velocidad de inferencia sin sacrificar precisión de forma relevante.
[] P: ¿El modelo cumplió el objetivo planteado?
[] R: Sí. El objetivo de diseño era una precisión de validación/prueba superior al 90%; el resultado real fue 97.02% de accuracy en el conjunto de prueba, superando ampliamente la meta.
[Heading 1] 6. Bloque: Sistema experto y decisión final
[] P: ¿Cómo funcionan exactamente las reglas del sistema experto?
[] R: Si la probabilidad de confianza es ≥85%: se acepta la clase (plástico o vidrio) y se clasifica mecánicamente. Si está entre 60% y 84%: se pide al usuario volver a acomodar el residuo para una nueva captura. Si es <60%: se marca como 'desconocido' en vez de forzar una clasificación poco confiable.
[] P: ¿Por qué separar el modelo de IA del sistema experto en vez de que la red decida directamente?
[] R: Porque permite ajustar los umbrales de aceptación (por ejemplo subir el umbral de 85% a 90% si se detectan más errores en producción) sin tener que reentrenar el modelo, y da trazabilidad explícita a los casos límite de confianza media o baja en vez de forzar siempre una respuesta binaria.
[] P: ¿Qué pasa con los datos después de que el sistema experto valida la predicción?
[] R: La transacción se envía a la plataforma web RePoints (dashboard construido con Node.js, React y Prisma ORM), que registra el resultado, lo hace trazable, y asigna/persiste los puntos de reciclaje en la cuenta del usuario de forma inmediata.
[Heading 1] 7. Preguntas 'trampa' y límites del proyecto
[] P: ¿El modelo fue probado con fotos reales tomadas en la universidad, con la cámara y la Raspberry Pi definitivas?
[] R: No todavía. Todo el entrenamiento y evaluación se hizo sobre el dataset de Kaggle (fotos domésticas, fondo controlado). Es una limitación reconocida explícitamente: el trabajo futuro es capturar imágenes reales en el campus con la Reverse Vending Machine instalada, para reentrenar y cerrar el 'domain shift' antes de producción definitiva.
[] P: ¿Qué pasaría si en producción aparece un objeto que no es ni plástico ni vidrio (por ejemplo metal o papel)?
[] R: Está fuera del alcance definido del proyecto: el sistema solo clasifica plástico vs. vidrio. Un objeto muy distinto probablemente caería en confianza baja (<60%) y el sistema experto lo marcaría como 'desconocido', pero no hay una clase dedicada para otros materiales en esta versión.
[] P: ¿No es un poco pequeño el dataset de prueba (403 imágenes) para confiar en el 97% de accuracy?
[] R: Es un tamaño razonable para un MVP académico con transfer learning, y el conjunto de prueba estuvo completamente aislado durante todo el entrenamiento (nunca se usó para ajustar hiperparámetros). Aun así, se reconoce como limitación que el test set comparte el mismo sesgo de fondo/ángulo que el resto del dataset, por lo que el número real en producción con fondos nuevos podría ser algo menor; de ahí la importancia de la validación futura con fotos del mundo real.
[] P: ¿Por qué eligieron una arquitectura binaria (plástico/vidrio) y no multiclase con más materiales desde el inicio?
[] R: Fue una decisión de alcance del proyecto integrador: el reto central es distinguir dos materiales visualmente similares (transparencia), no cubrir todo tipo de residuo. Ampliarlo a más clases queda como extensión futura.
[] P: ¿Cómo garantizan que el split de datos es reproducible?
[] R: Usando una semilla fija (random_state=42) en la división estratificada 70/15/15, de modo que cualquiera que corra el mismo notebook con el mismo dataset obtiene exactamente la misma partición de entrenamiento, validación y prueba.
